The following steps describe how to run CareCoins in both development and
production (Docker) modes.

The frontend is the Flutter app in fluterFront/ — one codebase for web, iOS and
Android.


System requirements

- Node.js v20.x or higher
- npm (bundled with Node.js)
- Flutter SDK 3.44 or higher (dart SDK ^3.5.0)
- PostgreSQL 16 (development mode only; Docker mode includes its own
  PostgreSQL container)
- Docker and Docker Compose (for containerised deployment)
- Xcode (iOS builds) / Android Studio (Android builds) — native targets only


Running in development mode

Open two terminal windows:

Terminal 1 - Backend:
  cd backend && npm install && npm run dev

Terminal 2 - Frontend, on whichever target you want:
  cd fluterFront && flutter pub get
  flutter run -d chrome --web-port=8080     # web
  flutter run                               # iOS simulator / connected device
  flutter run --dart-define=API_BASE=http://10.0.2.2:3000   # Android emulator

The backend listens on http://localhost:3000, which is also the app's default
API_BASE, so web and iOS need no dart-define. The Android emulator reaches the
host as 10.0.2.2, and a physical device needs your machine's LAN address
(--dart-define=API_BASE=http://192.168.x.x:3000).

Pin the web port with --web-port=8080. Flutter otherwise picks a random one,
and the backend's CORS allowlist (ALLOWED_ORIGINS) accepts only exact origins
— there is no wildcard, even in development.

`flutter run` lists only simulators that are already booted. If none appear,
run `open -a Simulator` (iOS) or start an AVD from Android Studio first.


Running with Docker Compose (recommended for testing)

  docker compose up --build -d

This starts four services: the PostgreSQL database, a one-shot db-init
container that applies the schema and every migration idempotently, the
Node.js backend API, and Nginx serving the Flutter web build. Nginx also
proxies /api and /uploads to the backend, so nothing else is exposed — this is
the same public path the iOS and Android apps use. The application will be
accessible at http://localhost.

Two files must exist before running; neither is committed:

  - backend/.env             (copy backend/.env.example and fill it in)
  - firebase-credentials.json  at the repo root — the Firebase service account
                               key, mounted read-only into the backend

db-init exits 0 once finished; that is normal and not an error.


Running the automated test suite

- Backend unit tests:   cd backend && npm test
- Flutter analyzer:     cd fluterFront && flutter analyze
- Flutter unit/widget:  cd fluterFront && flutter test

There is no automated end-to-end suite; see docs/automatic-testing-E2E.md.


Creating a test account

No pre-existing credentials are required for manual testing. Open the app
(http://localhost:8080 in development, http://localhost under Docker, or the
simulator) and either:

  - Register with any email address and password.
  - Sign in with a Google account via the Google button.

After authentication, a four-step setup wizard covers family details,
caregivers, who you care for, and a questionnaire that seeds starter tasks in
your language (choose "start empty" to skip seeding). To test multi-user
flows, register a second account and join the same family using the invite
link from the first account's Profile view.


Environment variables

Development mode:
  backend/.env holds the local configuration and is not committed;
  backend/.env.example documents every variable. The Flutter app takes its
  configuration from --dart-define flags (API_BASE, and optionally
  AUTH_EMULATOR, RC_IOS_KEY, RC_ANDROID_KEY), with Firebase config compiled in
  from lib/firebase_options.dart.

Docker mode:
  docker-compose.yml sets DATABASE_URL, PORT and NODE_ENV itself and reads
  everything else from backend/.env. There is no .env at the repo root.
  The compose file has no ${VAR} substitutions.
